ICS 108 · Lecture 14 · Instructor concept refresher

Exception handling

Reading an integer can fail because its text is malformed. Even a valid integer may violate a booking rule. This lecture separates normal work from recovery, adds a retry loop that makes progress, and moves validation into a method that can pass a checked exception to its caller.

The extra examples deliberately change the context while preserving the rule. new Scanner("cold 24") reads tokens from supplied text instead of the keyboard, making each result reproducible. Read each prediction before expanding its answer.

Mental model: Try the operation. If it throws, leave the normal path and select a compatible handler. The handler decides how to recover; a loop supplies the next attempt.

P1-C1 · 9.1, pp. 1–3

Input exceptions

An exception interrupts normal execution when an operation cannot finish.

Key rule

Scanner.nextInt() throws InputMismatchException for a token it cannot read as an int.

Explanation, example, and recovery

How it works and when it matters

The program expects a seat count. A word such as two, a decimal such as 2.5, or an integer outside int's range cannot be read by nextInt. The assignment does not finish. Without a matching handler in the call chain, the exception escapes main and ends the main thread.

int seats = scnr.nextInt();

Common mistakes

A negative integer is still an integer. nextInt does not enforce a booking rule such as 1 to 4.

Check and answer

Would -1 cause InputMismatchException? No. It fits int; range validation is added in Problem 3.

Another context: Quiz score input

The domain changes; a token still has to match the requested type.

Scanner scores = new Scanner("absent");
try {
   int score = scores.nextInt();
} catch (InputMismatchException e) {
   System.out.println("Score is not an integer.");
}

Result

Score is not an integer.

Predict a change: Would -5 fail at this read?

Check your prediction

No. -5 is a valid int. A score-range rule needs a separate check.

P1-C2 · 9.1, pp. 3–6

The try block

A try block contains operations whose exceptions a following handler can catch.

Key rule

When a statement throws, the rest of that try block is skipped.

Explanation, example, and recovery

How it works and when it matters

Place both the read and its success report inside try. With two as input, the read throws, so no seat report is printed. With 2, both statements finish and the catch is skipped. Earlier completed operations are not automatically undone.

try {
   int seats = scnr.nextInt();
   System.out.println("Seats requested: " + seats);
}

Common mistakes

Printing a success result after the catch can report a default or stale value. Keep the success report inside try.

Check and answer

After the failed read, does Java return to the next line inside try? No.

Another context: Array lookup

A different operation can throw; later statements in the same try are still skipped.

int[] marks = {80, 90};
try {
   System.out.println(marks[2]);
   System.out.println("Lookup finished.");
} catch (ArrayIndexOutOfBoundsException e) {
   System.out.println("No such position.");
}

Result

No such position.

Predict a change: What changes if marks[2] becomes marks[1]?

Check your prediction

It prints 90 and then Lookup finished. Array indices here are 0 and 1; index 2 is outside the array.

P1-C3 · 9.1, pp. 3–6

The catch block

A catch block handles an exception whose type matches its parameter.

Key rule

After a handler finishes normally, execution continues after the try/catch.

Explanation, example, and recovery

How it works and when it matters

The parameter e refers to the exception object. This handler prints a useful message for malformed input; it does not retry the read. Session complete is outside try/catch, so both the success and handled-failure paths reach it.

catch (InputMismatchException e) {
   System.out.println("Enter a whole number.");
}

Common mistakes

Catching an exception does not repair the input or repeat the operation. Recovery must be written explicitly.

Check and answer

For two, which lines print? Enter a whole number. then Session complete.

Another context: Integer division

A matching handler can finish normally, allowing execution after try/catch.

try {
   int groups = 0;
   System.out.println(12 / groups);
} catch (ArithmeticException e) {
   System.out.println("Cannot divide by zero.");
}
System.out.println("Next task.");

Result

Cannot divide by zero.
Next task.

Predict a change: Would catch(InputMismatchException e) handle this failure?

Check your prediction

No. Integer division by zero throws ArithmeticException. That unrelated handler would not match; Next task. would not run. Floating-point division is a different case.

P2-C1 · 9.1, pp. 6–9

Retrying an operation

A loop can repeat an operation after its exception is handled.

Key rule

Mark the operation finished only after every required step succeeds.

Explanation, example, and recovery

How it works and when it matters

Problem 2 puts the existing try/catch inside a loop. The flag remains true after a failed read and becomes false only after an integer is reported. Catch is inside the loop so one bad attempt does not abandon the whole repetition.

boolean needInput = true;
while (needInput && scnr.hasNext()) {
   // Try one read; set needInput false on success.
}

Common mistakes

Setting needInput to false in the handler prevents a retry. Keep that assignment on the success path.

Check and answer

For two 3, how many attempts occur? Two: one failure and one success.

Another context: Sensor reading retry

A failed attempt keeps the loop active; a successful attempt changes its condition.

Scanner sensor = new Scanner("offline 18");
boolean pending = true;
while (pending && sensor.hasNext()) {
   try {
      System.out.println(sensor.nextInt());
      pending = false;
   } catch (InputMismatchException e) { sensor.next(); }
}

Result

18

Predict a change: If pending = false moves into the handler, is 18 reached?

Check your prediction

No. The failed first attempt would stop the loop. The success flag belongs after the operation succeeds.

P2-C2 · 9.1, pp. 6–9

Discarding invalid input

Scanner leaves a mismatching token unread until the program consumes it.

Key rule

Consume the bad token before retrying nextInt.

Explanation, example, and recovery

How it works and when it matters

A token is a sequence of non-whitespace characters. next reads one token as text without requiring an integer. After nextInt rejects two, next removes two, leaving the later 3 available. The input contract treats each whitespace-separated token as one attempt.

catch (InputMismatchException e) {
   System.out.println("Enter a whole number.");
   scnr.next();
}

Common mistakes

Retrying without next repeats the same failure indefinitely. nextLine would discard the rest of the line, including a valid later attempt on that line.

Check and answer

For two 3 on one line, why choose next instead of nextLine? To discard only two and preserve 3.

Another context: Temperature tokens

Consuming only the bad token preserves the next token, even on the same line.

Scanner temperatures = new Scanner("cold 24");
try {
   temperatures.nextInt();
} catch (InputMismatchException e) {
   System.out.println(temperatures.next());
}
System.out.println(temperatures.nextInt());

Result

cold
24

Predict a change: What if nextLine() replaces next() in the handler?

Check your prediction

It consumes cold 24, the rest of the line. The final nextInt then has no token and throws NoSuchElementException. Cleanup must match the input format.

P2-C3 · Teaching addition; Scanner loop application

End of input

Scanner.hasNext() reports whether another token is available.

Key rule

Stop cleanly when input ends before a successful attempt.

Explanation, example, and recovery

How it works and when it matters

hasNext checks for any token, not specifically an integer, so malformed tokens still reach the catch. It does not consume input. In an interactive console it may wait for a token or an end-of-input signal. This guard prevents an empty input stream from being treated as a mismatch.

while (needInput && scnr.hasNext()) {
   // Read the available token.
}

Common mistakes

hasNextInt as the loop condition would stop on two and never demonstrate the recovery handler. InputMismatchException is not the exception for exhausted input.

Check and answer

For empty input in Problem 2, what prints? Only Session complete.

Another context: End of a data stream

hasNext checks availability without consuming a token; availability changes after a read.

Scanner values = new Scanner("7");
System.out.println(values.hasNext());
System.out.println(values.nextInt());
System.out.println(values.hasNext());

Result

true
7
false

Predict a change: What are the first and last results for an empty string?

Check your prediction

The first hasNext is false. The unguarded nextInt then throws NoSuchElementException, so no last result prints. Put the read behind the guard.

P3-C1 · 9.2, pp. 11–16

Throwing an exception

A throw statement creates an exceptional exit from the current operation.

Key rule

Reject an invalid value before printing a success report.

Explanation, example, and recovery

How it works and when it matters

An integer can be well formed but unsuitable for a booking. validateSeats accepts 1 through 4 inclusive; otherwise new constructs an Exception object and throw transfers control. The constructor stores the message, which getMessage later retrieves.

if (seats < 1 || seats > 4) {
   throw new Exception("Seats must be 1 to 4.");
}

Common mistakes

new Exception alone only creates an object. It does not throw it. A thrown exception does not automatically undo earlier changes.

Check and answer

For 0, does the success report run? No. The validation call throws first.

Another context: Quiz score validation

Parsing a value and accepting it under a domain rule are separate decisions.

int score = 105;
try {
   if (score < 0 || score > 100) {
      throw new Exception("Score out of range.");
   }
   System.out.println("Score accepted.");
} catch (Exception e) { System.out.println(e.getMessage()); }

Result

Score out of range.

Predict a change: Would 100 throw? Would -1 throw?

Check your prediction

100 is accepted; -1 throws. The condition defines the valid range, and throw interrupts the success path.

P3-C2 · 9.3, pp. 24–31

Declaring checked exceptions

A throws clause declares an exception that may leave a method.

Key rule

For a checked exception, catch it or declare it with throws.

Explanation, example, and recovery

How it works and when it matters

Exception itself is a checked type. validateSeats lets it escape, so its signature declares throws Exception. The caller catches it. InputMismatchException is unchecked: Java permits catching it, but the compiler does not require a catch or throws declaration for it.

static void validateSeats(int seats) throws Exception {
   // Reject an invalid seat count.
}

Common mistakes

throws does not handle an exception and does not throw one by itself. Removing throws from this method without adding a local catch prevents compilation.

Check and answer

Why does nextInt need no throws declaration in main? Its InputMismatchException is unchecked.

Another context: A method that may fail

throws declares a possible checked exception; it does not cause or handle the failure.

static void checkMark(int mark) throws Exception {
   if (mark < 0) throw new Exception("Negative mark.");
}
// Caller must catch or declare this checked exception.

Result

For checkMark(-1): Exception leaves the method.

Predict a change: If the body never executes throw, does throws Exception force a failure?

Check your prediction

No. A nonnegative mark completes normally. A caller must still satisfy catch-or-declare because the declaration permits a checked exception.

P3-C3 · 9.3, pp. 25–27

Exception propagation

An uncaught exception leaves a method and is considered by handlers around its call.

Key rule

A method call that throws does not complete normally.

Explanation, example, and recovery

How it works and when it matters

For 0, nextInt succeeds and consumes the token. validateSeats then throws. Control leaves that method and the caller's try block; the seat report and success flag are skipped. The caller decides to show the message and retry. The validation method stays independent of input and output.

int seats = scnr.nextInt();
validateSeats(seats);
System.out.println("Seats requested: " + seats);

Common mistakes

After handling, execution does not resume inside validateSeats or after its call within try. The loop starts a fresh attempt.

Check and answer

For 0 3, does the handler need next()? No. The 0 was already consumed successfully.

Another context: A failed helper call

A thrown exception crosses the method boundary and skips the rest of the caller’s try.

try {
   checkMark(-1);
   System.out.println("Saved.");
} catch (Exception e) {
   System.out.println("Not saved.");
}

Result

Not saved.

Predict a change: After the catch, does execution return to print Saved.?

Check your prediction

No. The call and its surrounding try ended exceptionally. Execution continues after the whole try/catch. This snippet uses checkMark from the preceding example.

P3-C4 · 9.2, pp. 16–23; 9.4, p. 36 limitation

Multiple handlers

Java selects the first compatible catch block for the thrown exception.

Key rule

Put a specific exception handler before a handler for its superclass.

Explanation, example, and recovery

How it works and when it matters

InputMismatchException is a subclass of Exception. The specific handler must come first so malformed input receives its own message and token cleanup. The later handler reports validation failures. Only one handler runs for a given thrown exception. Exception is broad and could catch other unintended failures; a custom checked type is deferred.

catch (InputMismatchException e) {
   // Discard the malformed token.
}
catch (Exception e) {
   System.out.println(e.getMessage());
}

Common mistakes

Putting catch(Exception) first makes the following InputMismatchException handler unreachable and fails compilation. Do not consume another token after a range error.

Check and answer

If the first handler matches, does the second run too? No.

Another context: Two failure types

The first compatible handler runs; a superclass handler must follow its subclasses.

try {
   int n = new Scanner("zero").nextInt();
   if (n == 0) throw new Exception("Zero is forbidden.");
} catch (InputMismatchException e) {
   System.out.println("Bad text.");
} catch (Exception e) { System.out.println(e.getMessage()); }

Result

Bad text.

Predict a change: If the text changes from zero to 0, which handler runs?

Check your prediction

The general Exception handler prints Zero is forbidden. Parsing succeeded, so the specific mismatch handler does not match the explicitly thrown Exception.

Readiness self-check

Why must only the malformed-input handler discard a token?

Reveal answer

nextInt leaves a malformed token unread. A range error occurs after nextInt consumed the integer, so discarding again would lose the next attempt.

  2. Handle the failure. The rest of try is skipped. catch prints Enter a whole number.
  3. Continue below try/catch. The final statement prints Session complete.

Handling permits continuation; it does not retry.
