Problem 1: Handle one booking attempt

Write a campus event booking program that reads one token. If it is a Java int, report the requested seat count. Otherwise, print Enter a whole number. Always finish with Session complete. Assume at least one token is supplied; seat limits will be added later.

Input:
two

Expected output:
Enter a whole number.
Session complete.

What new concepts does it have?

Students will learn Trace a failed read, handle it, and identify where execution continues.

  • P1-C1 · Input exceptions
  • P1-C2 · The try block
  • P1-C3 · The catch block

Complete code

In examples/problem-1: javac CampusBooking.java, then java CampusBooking. Enter the supplied input.

CampusBooking.javaComplete
import java.util.Scanner;
import java.util.InputMismatchException;

public class CampusBooking {
   public static void main(String[] args) {
      Scanner scnr = new Scanner(System.in);
      // P1-C2: Protect the read and success report.
      try {
         // P1-C1: A non-integer token interrupts this read.
         int seats = scnr.nextInt();
         System.out.println("Seats requested: " + seats);
      }
      // P1-C3: Handle the mismatch, then continue below.
      catch (InputMismatchException e) {
         System.out.println("Enter a whole number.");
      }
      System.out.println("Session complete.");
   }
}

Elaborated concepts for instructor reference

P1-C1 Input exceptions

Scanner.nextInt() throws InputMismatchException for a token it cannot read as an int.

The program expects a seat count. A word such as two, a decimal such as 2.5, or an integer outside int's range cannot be read by nextInt. The assignment does not finish. Without a matching handler in the call chain, the exception escapes main and ends the main thread.

Common mistakes: A negative integer is still an integer. nextInt does not enforce a booking rule such as 1 to 4.

P1-C2 The try block

When a statement throws, the rest of that try block is skipped.

Place both the read and its success report inside try. With two as input, the read throws, so no seat report is printed. With 2, both statements finish and the catch is skipped. Earlier completed operations are not automatically undone.

Common mistakes: Printing a success result after the catch can report a default or stale value. Keep the success report inside try.

P1-C3 The catch block

After a handler finishes normally, execution continues after the try/catch.

The parameter e refers to the exception object. This handler prints a useful message for malformed input; it does not retry the read. Session complete is outside try/catch, so both the success and handled-failure paths reach it.

Common mistakes: Catching an exception does not repair the input or repeat the operation. Recovery must be written explicitly.

Trace: Step-by-step execution

  1. Read the token.

    nextInt sees two and throws InputMismatchException; seats is not assigned.

  2. Handle the failure.

    The rest of try is skipped. catch prints Enter a whole number.

  3. Continue below try/catch.

    The final statement prints Session complete.

Key point: Handling permits continuation; it does not retry.

Practice and answer: Predict input 2, then run it: Seats requested: 2 followed by Session complete. Compare the path with two.

Problem 2: Retry a malformed attempt

Extend Problem 1 so malformed input produces the same message and another attempt is allowed. Treat each whitespace-separated token as one attempt. Stop after reporting the first integer, or when input ends. Keep the final Session complete. message.

Input:
two 3

Expected output:
Enter a whole number.
Seats requested: 3
Session complete.

What new concepts does it have?

Students will learn Retry safely by consuming the failed token and checking for end of input.

  • P2-C1 · Retrying an operation
  • P2-C2 · Discarding invalid input
  • P2-C3 · End of input

Complete code

In examples/problem-2: javac CampusBooking.java, then java CampusBooking. Enter the supplied input.

CampusBooking.javaComplete
import java.util.Scanner;
import java.util.InputMismatchException;

public class CampusBooking {
   public static void main(String[] args) {
      Scanner scnr = new Scanner(System.in);
      // P2-C1: Repeat until one read succeeds.
      boolean needInput = true;
      // P2-C3: Stop if there are no more tokens.
      while (needInput && scnr.hasNext()) {
         try {
            int seats = scnr.nextInt();
            System.out.println("Seats requested: " + seats);
            needInput = false;
         }
         catch (InputMismatchException e) {
            System.out.println("Enter a whole number.");
            // P2-C2: Remove only the rejected token.
            scnr.next();
         }
      }
      System.out.println("Session complete.");
   }
}

Elaborated concepts for instructor reference

P2-C1 Retrying an operation

Mark the operation finished only after every required step succeeds.

Problem 2 puts the existing try/catch inside a loop. The flag remains true after a failed read and becomes false only after an integer is reported. Catch is inside the loop so one bad attempt does not abandon the whole repetition.

Common mistakes: Setting needInput to false in the handler prevents a retry. Keep that assignment on the success path.

P2-C2 Discarding invalid input

Consume the bad token before retrying nextInt.

A token is a sequence of non-whitespace characters. next reads one token as text without requiring an integer. After nextInt rejects two, next removes two, leaving the later 3 available. The input contract treats each whitespace-separated token as one attempt.

Common mistakes: Retrying without next repeats the same failure indefinitely. nextLine would discard the rest of the line, including a valid later attempt on that line.

P2-C3 End of input

Stop cleanly when input ends before a successful attempt.

hasNext checks for any token, not specifically an integer, so malformed tokens still reach the catch. It does not consume input. In an interactive console it may wait for a token or an end-of-input signal. This guard prevents an empty input stream from being treated as a mismatch.

Common mistakes: hasNextInt as the loop condition would stop on two and never demonstrate the recovery handler. InputMismatchException is not the exception for exhausted input.

Trace: Step-by-step execution

  1. First attempt: two.

    hasNext is true. nextInt fails and the handler prints Enter a whole number.

  2. Remove the failed token.

    next consumes two. needInput remains true.

  3. Second attempt: 3.

    nextInt returns 3. The program reports Seats requested: 3 and sets needInput false.

  4. Leave the loop.

    The final statement prints Session complete.

Key point: A retry needs both repetition and progress through the input.

Practice and answer: Try two 3 on one line and on separate lines: output is identical. Empty input prints only Session complete.

Problem 3: Validate the seat count

Extend Problem 2 so only 1 to 4 seats can be requested. For an integer outside this range, print Seats must be 1 to 4. and allow another attempt. Retain malformed-input recovery, token-by-token attempts, end-of-input handling, and the final message. Stop after the first valid booking.

two 0 3

Expected output:
Enter a whole number.
Seats must be 1 to 4.
Seats requested: 3
Session complete.

What new concepts does it have?

Students will learn Throw and propagate a checked exception, then select the appropriate handler.

  • P3-C1 · Throwing an exception
  • P3-C2 · Declaring checked exceptions
  • P3-C3 · Exception propagation
  • P3-C4 · Multiple handlers

Complete code

In examples/problem-3: javac CampusBooking.java, then java CampusBooking. Enter the supplied input.

CampusBooking.javaComplete
import java.util.Scanner;
import java.util.InputMismatchException;

public class CampusBooking {
   // P3-C2: Declare the checked exception for callers.
   static void validateSeats(int seats) throws Exception {
      if (seats < 1 || seats > 4) {
         // P3-C1: Reject before reporting success.
         throw new Exception("Seats must be 1 to 4.");
      }
   }
   public static void main(String[] args) {
      Scanner scnr = new Scanner(System.in);
      boolean needInput = true;
      while (needInput && scnr.hasNext()) {
         try {
            int seats = scnr.nextInt();
            // P3-C3: A failure leaves this call and try.
            validateSeats(seats);
            System.out.println("Seats requested: " + seats);
            needInput = false;
         }
         // P3-C4: Specific handler before general handler.
         catch (InputMismatchException e) {
            System.out.println("Enter a whole number.");
            scnr.next();
         }
         catch (Exception e) {
            System.out.println(e.getMessage());
         }
      }
      System.out.println("Session complete.");
   }
}

Elaborated concepts for instructor reference

P3-C1 Throwing an exception

Reject an invalid value before printing a success report.

An integer can be well formed but unsuitable for a booking. validateSeats accepts 1 through 4 inclusive; otherwise new constructs an Exception object and throw transfers control. The constructor stores the message, which getMessage later retrieves.

Common mistakes: new Exception alone only creates an object. It does not throw it. A thrown exception does not automatically undo earlier changes.

P3-C2 Declaring checked exceptions

For a checked exception, catch it or declare it with throws.

Exception itself is a checked type. validateSeats lets it escape, so its signature declares throws Exception. The caller catches it. InputMismatchException is unchecked: Java permits catching it, but the compiler does not require a catch or throws declaration for it.

Common mistakes: throws does not handle an exception and does not throw one by itself. Removing throws from this method without adding a local catch prevents compilation.

P3-C3 Exception propagation

A method call that throws does not complete normally.

For 0, nextInt succeeds and consumes the token. validateSeats then throws. Control leaves that method and the caller's try block; the seat report and success flag are skipped. The caller decides to show the message and retry. The validation method stays independent of input and output.

Common mistakes: After handling, execution does not resume inside validateSeats or after its call within try. The loop starts a fresh attempt.

P3-C4 Multiple handlers

Put a specific exception handler before a handler for its superclass.

InputMismatchException is a subclass of Exception. The specific handler must come first so malformed input receives its own message and token cleanup. The later handler reports validation failures. Only one handler runs for a given thrown exception. Exception is broad and could catch other unintended failures; a custom checked type is deferred.

Common mistakes: Putting catch(Exception) first makes the following InputMismatchException handler unreachable and fails compilation. Do not consume another token after a range error.

Trace: Step-by-step execution

  1. two fails to parse.

    The specific handler prints Enter a whole number. and consumes two.

  2. 0 parses but fails validation.

    validateSeats(0) throws Exception. The general handler prints Seats must be 1 to 4.; 0 is already consumed.

  3. 3 succeeds.

    validateSeats(3) returns normally. The report prints Seats requested: 3 and needInput becomes false.

  4. Finish.

    The loop stops; Session complete. prints.

Key point: Parsing failure leaves a token unread; validation failure occurs after it was consumed.

Practice and answer: Try 1 and 4 (accepted), then 0 5 4 (two range messages, one successful report). Remove throws, compile, then restore it and rerun.
