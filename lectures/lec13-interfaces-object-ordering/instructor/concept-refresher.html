Interfaces and ordering objects

Interfaces describe operations a type promises to provide. The employee program first exposes its bonus operation through a small interface, then adopts Java’s Comparable interface so library code can order its records.

Mental model: An interface states what a caller may ask. The implementing class supplies the behavior. Comparable gives the sorting library one consistent comparison operation.

P1-C1 · 8.10, pp. 57–62

Interfaces

An interface declares a contract that implementing classes agree to provide.

Key rule

An interface declares a contract that implementing classes agree to provide.

Explanation, example, and recovery

How it works and when it matters

Payable describes a capability: producing an integer bonus. In this simple declaration, getBonus is implicitly public and abstract. A future unrelated class could implement the same capability. Interface variables can hold implementing objects, but new Payable() does not instantiate the interface itself.

interface Payable {
   int getBonus();
}

Common error and recovery

Do not add a method body to this plain abstract declaration. Default and static interface methods are possible in Java, but are outside this small example.

Check and answer

Must a payable object be an Employee? No; any class may implement the contract.

P1-C2 · 8.10, pp. 57–61

Implementing an interface

implements declares that a class satisfies an interface’s contract.

Key rule

implements declares that a class satisfies an interface’s contract.

Explanation, example, and recovery

How it works and when it matters

Employee names the contract and keeps getBonus abstract. Its concrete subclasses fulfill it, so both Manager and StudentEmployee are Payable. A concrete implementing class must provide public implementations of required methods. A class can extend one class and implement several interfaces.

abstract class Employee implements Payable {
   public abstract int getBonus();
}

Common error and recovery

Reducing getBonus visibility breaks the public contract. Restore public in the declaration and concrete methods.

Check and answer

Does each subclass need to repeat implements Payable? No; the relationship is inherited.

P1-C3 · 8.10, pp. 57–62; application of 8.5

Interface references

An interface reference can refer to an object whose class implements that interface.

Key rule

An interface reference can refer to an object whose class implements that interface.

Explanation, example, and recovery

How it works and when it matters

payment only needs the getBonus contract. Passing the manager yields 50; passing the student yields 30. Dynamic dispatch still chooses the actual object’s implementation. The parameter deliberately cannot call getName because Payable does not declare that operation.

static int payment(Payable item) {
   return item.getBonus();
}

Common error and recovery

Adding item.getName() fails on a Payable parameter. Keep the payment routine focused on its declared contract.

Check and answer

Could the routine accept a different payable class with no employee name? Yes; no employee-specific operation is used.

P1-C4 · 8.10, pp. 58–61

Abstract classes and interfaces

An abstract class can share instance state; an interface can express a capability across different class families.

Key rule

An abstract class can share instance state; an interface can express a capability across different class families.

Explanation, example, and recovery

How it works and when it matters

Employee shares a name field, constructor, accessor, and text representation. Payable promises one operation without employee instance state. Modern interfaces may also contain default, static, and private methods; do not teach that interfaces can never contain code. The distinction here is shared employee implementation versus a reusable payment capability.

abstract class Employee implements Payable {
   private String name;
   public abstract int getBonus();
}

Common error and recovery

Moving the name into the interface does not create a per-employee mutable field; interface fields are constants. Keep instance state in Employee.

Check and answer

For a name stored per employee, choose the abstract class. For a bonus capability used by unrelated classes, choose the interface.

P2-C1 · 8.11, pp. 64–70

The Comparable interface

Comparable<T> gives a type a natural ordering through compareTo(T other).

Key rule

Comparable<T> gives a type a natural ordering through compareTo(T other).

Explanation, example, and recovery

How it works and when it matters

Employee is the comparison type, so an Employee is compared with another Employee, including subclass objects. This uses a parameterized interface without teaching generic class design. Comparable is in java.lang and needs no explicit import. Payable remains implemented: adding ordering does not remove payment behavior.

abstract class Employee
      implements Payable, Comparable<Employee> {
   public int compareTo(Employee other) {
      return getName().compareTo(other.getName());
   }
}

Common error and recovery

Avoid raw Comparable: it loses the useful Employee parameter type. Keep Comparable<Employee> and the matching compareTo signature.

Check and answer

Can Manager and StudentEmployee be compared? Yes; both are Employee objects using the same ordering rule.

P2-C2 · 8.11, pp. 64–67

The compareTo result

compareTo returns a negative, zero, or positive number for before, tied, or after.

Key rule

compareTo returns a negative, zero, or positive number for before, tied, or after.

Explanation, example, and recovery

How it works and when it matters

The sign is the contract, not an exact value of minus one or plus one. String comparison makes Omar positive relative to Nora, so the report prints true for “Omar after Nora.” Reversing the comparison reverses its sign for unequal names. Comparing an employee with itself gives zero.

int result = first.compareTo(second);
// result < 0: first before second
// result == 0: tied in ordering
// result > 0: first after second

Common error and recovery

Testing result == 1 incorrectly assumes a particular magnitude. Use result > 0 when asking whether one item belongs after another.

Check and answer

Two employees with the same name compare as zero. Does that merge or delete them? No; comparison alone changes nothing.

P2-C3 · 8.11, pp. 64–70

A consistent ordering rule

A natural ordering must compare all objects using one consistent rule.

Key rule

A natural ordering must compare all objects using one consistent rule.

Explanation, example, and recovery

How it works and when it matters

All employee kinds compare names using String.compareTo. This is case-sensitive lexicographic ordering, not locale-aware dictionary sorting. It is transitive and uses the same criterion for every pair. Name equality in ordering does not override Object.equals. That difference matters in sorted sets; those collections are deferred.

public int compareTo(Employee other) {
   return getName().compareTo(other.getName());
}

Common error and recovery

Do not compare managers by bonus but students by name inside the same ordering method. Use a common criterion for every Employee.

Check and answer

For Ali, Nora, and Omar, predict the ascending order. It is Ali, Nora, Omar under the stated capitalization constraint.

P3-C1 · 8.11, pp. 62–70

Library sorting

Collections.sort(list) sorts a modifiable list using its elements’ natural ordering.

Key rule

Collections.sort(list) sorts a modifiable list using its elements’ natural ordering.

Explanation, example, and recovery

How it works and when it matters

The library calls the Employee comparison operation as needed. Students supply the ordering rule, while the library performs the algorithm. Import java.util.Collections separately from java.util.ArrayList; Collections is a utility class, not the list’s element type. Sorting algorithm design belongs to the later syllabus sessions.

Collections.sort(staff);

Common error and recovery

Without Comparable<Employee>, this no-comparator sort cannot order these employee objects. Restore the interface and compareTo implementation.

Check and answer

Does importing Collections sort anything automatically? No; the program must call sort.

P3-C2 · 8.11, pp. 62–70

Sorting changes list order

Sorting rearranges the references in the existing list without replacing the employee objects.

Key rule

Sorting rearranges the references in the existing list without replacing the employee objects.

Explanation, example, and recovery

How it works and when it matters

Collections.sort returns void; it modifies the supplied list. Nora’s object still stores 10 hours and returns 30. Omar remains a Manager with bonus 50. The list size is unchanged. A separate variable holding one employee reference still reaches that same object after sorting.

Collections.sort(staff);
// staff now visits Nora before Omar

Common error and recovery

Do not write staff = Collections.sort(staff); there is no returned list to assign. Call sort as a statement, then read the existing list.

Check and answer

After sorting, which object does staff.get(0) reach? Nora. Did Nora’s class or bonus change? No.

P3-C3 · 8.5 and 8.11; 8.10 interface UML pp. 59–61

Ordering and polymorphism

Reordering references changes traversal order while overridden methods keep their behavior.

Key rule

Reordering references changes traversal order while overridden methods keep their behavior.

Explanation, example, and recovery

How it works and when it matters

The shared printStaff loop is used before and after sorting. After sorting it visits Nora first and Omar second, but payment still dispatches to the correct bonus rule. In UML, an interface realization uses a dashed line with a hollow triangle toward the interface; this differs from the solid inheritance line. The refresher diagram links Employee to Payable and Comparable.

for (Employee employee : staff) {
   System.out.println(employee + " | Bonus: " + payment(employee));
}

Common error and recovery

Do not swap employee names to simulate sorted output. That changes data and may attach the wrong name to a bonus. Sort the list references.

Check and answer

If two names tie, Collections.sort is stable: their prior relative order remains. They are still two separate records.

Class relationship reference

Solid line and hollow triangle: inheritance. Dashed line and hollow triangle: interface realization. The triangle points toward the more general type.

Employee ◁──── StudentEmployee
Employee ◁──── Manager
Payable  ◁┄┄┄┄ Employee
Comparable<Employee> ◁┄┄┄┄ Employee

The last two relationships apply in Lecture 13. In Lecture 12’s final version, write Employee and getBonus in italics in a UML diagram because they are abstract. A minus marks a private member, plus public, and hash protected.

Readiness self-check

If compareTo returns 0 for two employees, must they be the same object?

Reveal answer

No. Here it means their names occupy the same position in the ordering. Their identity and Object.equals result can still differ.

Problem 1: trace and practice

The Employee hierarchy and report are retained. payment receives each object through Payable: Omar yields 50 and Nora 30. No object is copied or converted to a different runtime class.

Try to call getName through Payable. Explain the compile-time restriction and restore the bonus-only routine.

Problem 2: trace and practice

The original report remains in insertion order. The comparison uses Omar against Nora; its result is positive, so the added line is true. No sorting has happened yet.

Compare Nora with Omar, then Nora with Nora. Check for a negative result and zero without assuming a particular negative magnitude.

Original output: Omar 50, Nora 30, comparison true. Sorted output: Nora 30, Omar 50. The report implementation, payment interface, abstract hierarchy, and comparison rule are all retained.

Try an empty list, a one-entry list, and two distinct records with the same name. Check size, bonuses, and tie order after sorting.
