Problem 1: Provide a payment contract

Continue the previous employee program with Omar the manager and Nora the student employee. Add a reusable payment operation that accepts any object promising a bonus amount. Keep the existing employee report and bonus values unchanged.

Omar | Bonus: 50

Complete code

In examples/problem-1: javac CampusPayroll.java, then java CampusPayroll. Pause at the matching concept comments.

CampusPayroll.javaComplete
import java.util.ArrayList;

// P1-C1: An interface states a required operation.
interface Payable {
   int getBonus();
}
// P1-C2: Employee adopts the Payable contract.
// P1-C4: The abstract class keeps shared employee state.
abstract class Employee implements Payable {
   private String name;
   public Employee(String name) { this.name = name; }
   public String getName() { return name; }
   public abstract int getBonus();
   @Override
   public String toString() { return name; }
}
class StudentEmployee extends Employee {
   private int hours;
   public StudentEmployee(String name, int hours) {
      super(name);
      this.hours = hours;
   }
   public int getHours() { return hours; }
   @Override
   public int getBonus() { return 20 + hours; }
}
class Manager extends Employee {
   public Manager(String name) { super(name); }
   @Override
   public int getBonus() { return 50; }
}
public class CampusPayroll {
   // P1-C3: This parameter depends on the interface.
   public static int payment(Payable item) { return item.getBonus(); }
   public static void printStaff(ArrayList<Employee> staff) {
      for (Employee employee : staff) {
         System.out.println(employee + " | Bonus: " + payment(employee));
      }
   }
   public static void main(String[] args) {
      ArrayList<Employee> staff = new ArrayList<Employee>();
      staff.add(new Manager("Omar"));
      staff.add(new StudentEmployee("Nora", 10));
      printStaff(staff);
   }
}

Elaborated concepts for instructor reference

P1-C1 Interfaces

An interface declares a contract that implementing classes agree to provide.

Payable describes a capability: producing an integer bonus. In this simple declaration, getBonus is implicitly public and abstract. A future unrelated class could implement the same capability. Interface variables can hold implementing objects, but new Payable() does not instantiate the interface itself.

Common mistakes: Do not add a method body to this plain abstract declaration. Default and static interface methods are possible in Java, but are outside this small example.

P1-C2 Implementing an interface

implements declares that a class satisfies an interface’s contract.

Employee names the contract and keeps getBonus abstract. Its concrete subclasses fulfill it, so both Manager and StudentEmployee are Payable. A concrete implementing class must provide public implementations of required methods. A class can extend one class and implement several interfaces.

Common mistakes: Reducing getBonus visibility breaks the public contract. Restore public in the declaration and concrete methods.

P1-C3 Interface references

An interface reference can refer to an object whose class implements that interface.

payment only needs the getBonus contract. Passing the manager yields 50; passing the student yields 30. Dynamic dispatch still chooses the actual object’s implementation. The parameter deliberately cannot call getName because Payable does not declare that operation.

Common mistakes: Adding item.getName() fails on a Payable parameter. Keep the payment routine focused on its declared contract.

P1-C4 Abstract classes and interfaces

An abstract class can share instance state; an interface can express a capability across different class families.

Employee shares a name field, constructor, accessor, and text representation. Payable promises one operation without employee instance state. Modern interfaces may also contain default, static, and private methods; do not teach that interfaces can never contain code. The distinction here is shared employee implementation versus a reusable payment capability.

Common mistakes: Moving the name into the interface does not create a per-employee mutable field; interface fields are constants. Keep instance state in Employee.

Trace: Step-by-step execution

  1. Create the two employee objects.

    main adds Omar, a Manager, then Nora, a StudentEmployee with hours = 10. The list order is [Omar, Nora].

  2. Print Omar’s record.

    printStaff(staff) visits Omar first. payment(employee) receives the same object through a Payable reference. Its call to item.getBonus() runs Manager.getBonus(), which returns 50. toString() supplies the name Omar.

    Output
    Omar | Bonus: 50
  3. Print Nora’s record.

    The loop visits Nora next. This time, item.getBonus() runs StudentEmployee.getBonus(): 20 + hours = 20 + 10 = 30. toString() supplies the name Nora.

    Output
    Nora | Bonus: 30

Key point: The same payment method calls the bonus implementation belonging to each object’s actual class.

Practice: Try to call getName through Payable. Explain the compile-time restriction and restore the bonus-only routine.

Complete code

In examples/problem-2: javac CampusPayroll.java, then java CampusPayroll. Pause at the matching concept comments.

CampusPayroll.javaComplete
import java.util.ArrayList;

interface Payable {
   int getBonus();
}
// P2-C1: Comparable<Employee> supplies typed natural ordering.
abstract class Employee implements Payable, Comparable<Employee> {
   private String name;
   @Override
   // P2-C2: The result sign describes this name relative to the other.
   public int compareTo(Employee other) {
      // P2-C3: Delegate to String's consistent name ordering.
      return name.compareTo(other.name);
   }
   public Employee(String name) { this.name = name; }
   public String getName() { return name; }
   public abstract int getBonus();
   @Override
   public String toString() { return name; }
}
class StudentEmployee extends Employee {
   private int hours;
   public StudentEmployee(String name, int hours) {
      super(name);
      this.hours = hours;
   }
   public int getHours() { return hours; }
   @Override
   public int getBonus() { return 20 + hours; }
}
class Manager extends Employee {
   public Manager(String name) { super(name); }
   @Override
   public int getBonus() { return 50; }
}
public class CampusPayroll {
   public static int payment(Payable item) { return item.getBonus(); }
   public static void printStaff(ArrayList<Employee> staff) {
      for (Employee employee : staff) {
         System.out.println(employee + " | Bonus: " + payment(employee));
      }
   }
   public static void main(String[] args) {
      ArrayList<Employee> staff = new ArrayList<Employee>();
      staff.add(new Manager("Omar"));
      staff.add(new StudentEmployee("Nora", 10));
      printStaff(staff);
      System.out.println("Omar after Nora: " +
            (staff.get(0).compareTo(staff.get(1)) > 0));
   }
}

Elaborated concepts for instructor reference

P2-C1 The Comparable interface

Comparable<T> gives a type a natural ordering through compareTo(T other).

Employee is the comparison type, so an Employee is compared with another Employee, including subclass objects. This uses a parameterized interface without teaching generic class design. Comparable is in java.lang and needs no explicit import. Payable remains implemented: adding ordering does not remove payment behavior.

Common mistakes: Avoid raw Comparable: it loses the useful Employee parameter type. Keep Comparable<Employee> and the matching compareTo signature.

P2-C2 The compareTo result

compareTo returns a negative, zero, or positive number for before, tied, or after.

The sign is the contract, not an exact value of minus one or plus one. String comparison makes Omar positive relative to Nora, so the report prints true for “Omar after Nora.” Reversing the comparison reverses its sign for unequal names. Comparing an employee with itself gives zero.

Common mistakes: Testing result == 1 incorrectly assumes a particular magnitude. Use result > 0 when asking whether one item belongs after another.

P2-C3 A consistent ordering rule

A natural ordering must compare all objects using one consistent rule.

All employee kinds compare names using String.compareTo. This is case-sensitive lexicographic ordering, not locale-aware dictionary sorting. It is transitive and uses the same criterion for every pair. Name equality in ordering does not override Object.equals. That difference matters in sorted sets; those collections are deferred.

Common mistakes: Do not compare managers by bonus but students by name inside the same ordering method. Use a common criterion for every Employee.

Trace: Step-by-step execution

  1. Print the original staff report.

    main creates the list in the order [Omar, Nora]. printStaff(staff) visits each object and calculates its bonus as in Problem 1.

    Output
    Omar | Bonus: 50
Nora | Bonus: 30
  2. Compare Omar with Nora.

    staff.get(0) is Omar; staff.get(1) is Nora. The call staff.get(0).compareTo(staff.get(1)) runs Employee.compareTo with Omar as the current object and Nora as other.

    Inside the method, name.compareTo(other.name) becomes "Omar".compareTo("Nora"). It returns a positive number because O comes after N.

  3. Check the sign and print the result.

    The condition compareTo(...) > 0 is true, so the program prints:

    Output

Key point: Comparing two employees does not rearrange the list. Its order is still [Omar, Nora].

Practice: Compare Nora with Omar, then Nora with Nora. Check for a negative result and zero without assuming a particular negative magnitude.

Complete code

In examples/problem-3: javac CampusPayroll.java, then java CampusPayroll. Pause at the matching concept comments.

CampusPayroll.javaComplete
import java.util.ArrayList;
// P3-C1: Import the sorting utility.
import java.util.Collections;

interface Payable {
   int getBonus();
}
abstract class Employee implements Payable, Comparable<Employee> {
   private String name;
   @Override
   public int compareTo(Employee other) {
      return name.compareTo(other.name);
   }
   public Employee(String name) { this.name = name; }
   public String getName() { return name; }
   public abstract int getBonus();
   @Override
   public String toString() { return name; }
}
class StudentEmployee extends Employee {
   private int hours;
   public StudentEmployee(String name, int hours) {
      super(name);
      this.hours = hours;
   }
   public int getHours() { return hours; }
   @Override
   public int getBonus() { return 20 + hours; }
}
class Manager extends Employee {
   public Manager(String name) { super(name); }
   @Override
   public int getBonus() { return 50; }
}
public class CampusPayroll {
   public static int payment(Payable item) { return item.getBonus(); }
   public static void printStaff(ArrayList<Employee> staff) {
      for (Employee employee : staff) {
         System.out.println(employee + " | Bonus: " + payment(employee));
      }
   }
   public static void main(String[] args) {
      ArrayList<Employee> staff = new ArrayList<Employee>();
      staff.add(new Manager("Omar"));
      staff.add(new StudentEmployee("Nora", 10));
      printStaff(staff);
      System.out.println("Omar after Nora: " +
            (staff.get(0).compareTo(staff.get(1)) > 0));
      // P3-C2: Sort references in this list.
      Collections.sort(staff);
      System.out.println("Sorted:");
      // P3-C3: Each object keeps its bonus rule.
      printStaff(staff);
   }
}

Elaborated concepts for instructor reference

P3-C1 Library sorting

Collections.sort(list) sorts a modifiable list using its elements’ natural ordering.

The library calls the Employee comparison operation as needed. Students supply the ordering rule, while the library performs the algorithm. Import java.util.Collections separately from java.util.ArrayList; Collections is a utility class, not the list’s element type. Sorting algorithm design belongs to the later syllabus sessions.

Common mistakes: Without Comparable<Employee>, this no-comparator sort cannot order these employee objects. Restore the interface and compareTo implementation.

P3-C2 Sorting changes list order

Sorting rearranges the references in the existing list without replacing the employee objects.

Collections.sort returns void; it modifies the supplied list. Nora’s object still stores 10 hours and returns 30. Omar remains a Manager with bonus 50. The list size is unchanged. A separate variable holding one employee reference still reaches that same object after sorting.

Common mistakes: Do not write staff = Collections.sort(staff); there is no returned list to assign. Call sort as a statement, then read the existing list.

P3-C3 Ordering and polymorphism

Reordering references changes traversal order while overridden methods keep their behavior.

The shared printStaff loop is used before and after sorting. After sorting it visits Nora first and Omar second, but payment still dispatches to the correct bonus rule. In UML, an interface realization uses a dashed line with a hollow triangle toward the interface; this differs from the solid inheritance line. The refresher diagram links Employee to Payable and Comparable.

Common mistakes: Do not swap employee names to simulate sorted output. That changes data and may attach the wrong name to a bonus. Sort the list references.
